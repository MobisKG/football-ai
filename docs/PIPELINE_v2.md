# Полный прогон, издание 2: план на месте, дешёвая качалка, много коротких машин

Код: `scripts/full_run/`, навык `.claude/skills/full-run`, серверная часть `server/`.
Прогон 14–15.09 (`scripts/batch_run.py`) работал иначе: 4 машины по очереди тянули
видео сами, а ноутбук считал процессорные шаги. Отсюда три беды: прогон шёл 4,5 часа,
зависел от включённого ноутбука, и дорогая машина с видеокартой простаивала, пока
YouTube отказывался отдавать ей видео. Издание 2 разводит эти роли.

## Этапы

**1. План — на управляющей машине, до аренды.** `full_run/channel.py` берёт список
канала (`yt-dlp --flat-playlist`, ставится в свой кэш, если его нет) и выкидывает
видео, которые уже разбирались в прошлых прогонах (`results/*/jobs.json`,
`results/*/matches.json`). Получается `<outdir>/plan.json`: имя, ролик, название,
длительность, место для `match_guid`. Здесь же печатается, сколько будет машин,
времени и денег. Ничего ещё не арендовано — план можно посмотреть и поправить.

**2. Качалка — одна дешёвая машина.** Без видеокарты (`cpuFlavorIds`, диск 40 ГБ,
~0,1 $/ч против 0,5–0,7 $/ч у машины с видеокартой). Скачивает все видео подряд,
проверяя каждое по последнему видеопакету, а не по заголовку: обрезанная передача
уже один раз дала разбор 75 % игры. YouTube пускает не с каждого адреса RunPod;
если два видео подряд получили «Sign in to confirm you're not a bot», машина
удаляется, берётся другая, список продолжается с того же места (до 4 замен).
Если процессорные машины не выдаются, качалка берёт самую дешёвую с видеокартой.

**3. Раздача — по две игры на машину.** Машин `ceil(игр / --per-pod)`: 24 игры → 12
машин. Игры раскладываются змейкой по убыванию длительности, чтобы машины
освободились примерно вместе. Каждая машина получает **только свои** видео и берёт
их прямо с качалки (`scp` между машинами по общему ключу, управляющий узел файлы
не перекачивает). Когда все получили — качалка удаляется, дальше платим только за
рабочие машины.

**4. Разбор — машина работает сама.** `full_run/pod_job.sh` запускается через
`nohup` и ни одного шага не ждёт снаружи: видеокарта (`run_video.sh` →
`run_gpu_match.sh`), затем процессорные шаги на той же машине
(`full_run/pod_cpu_steps.py`: мяч, команды, номера, re-id, статистика, хозяева).
Раньше это считал мак — из-за этого прогон и зависел от ноутбука. Пять–семь минут
машины стоят около 0,05 $, зато управляющий узел больше ни при чём. По каждой игре
появляется метка `out/<игра>.READY`, по всем — `out/ALL_DONE`. Видео после разбора
удаляется: на диске 60 ГБ помещается следующее.

**5. Сбор и загрузка — по мере готовности.** Сторож обходит машины раз в две
минуты, забирает готовые игры (маленькие json, полный архив — следом), грузит на
сайт `upload_analytics.py` и проверяет чтением. Когда все игры машины собраны, она
удаляется, не дожидаясь остальных. В конце список машин проверяется через API.

**Токен сайта на арендованные машины не попадает.** Грузит тот, у кого он есть:
ноутбук или сервер. Машина отдаёт только статистику.

## Числа

| | издание 1 (14–15.09) | издание 2 |
|---|---|---|
| машин | 4 | 12 рабочих + 1 качалка |
| время на 24 игры | 4,5 ч | 2–2,5 ч |
| деньги | 20,84 $ | ~20–25 $ (те же часы видеокарты, дороже только установка) |
| нужен ноутбук | да, всё время | нет |
| простой дорогой машины на скачивании | да | нет |

Время машины: 1,2–1,4 минуты на минуту записи при 15 кадрах в секунду, плюс 3–6
минут установки. Две игры по 40 минут — около 2 часов. Хотите короче — `--per-pod 1`
(24 машины, ~1,2 ч), дороже на установку; хотите дешевле — `--per-pod 3`.

## Запуск

```bash
cd football/scripts
python -m full_run.run --dry-run             # план и оценка, без аренды
python -m full_run.run --per-pod 2           # прогон с ноутбука
python -m full_run.remote deploy             # залить код на сервер
python -m full_run.remote start --per-pod 2  # прогон на сервере, ноутбук не нужен
python -m full_run.remote status             # этап, игры, деньги
```

Ключи: `football/.env` → `KEY=` (RunPod); `~/Documents/sport/.env` → `SPORTX_TOKEN`
или пара `SPORTX_USER`/`SPORTX_PASS`. Токен сайта протухает, поэтому
`full_run/site.py` при отказе логинится заново и кладёт свежий в `~/.cache/fb/token`.

## Сервер вместо ноутбука

`server/` ставится рядом с sportbox на 46.101.9.74: свой контейнер
`football-runner`, свои папки, портов наружу нет, чужого не трогает.

```bash
# на ноутбуке (один раз): доступ по ключу
ssh-copy-id root@46.101.9.74
python -m full_run.remote deploy
# на сервере: заполнить /opt/football-runner/env (ключ RunPod, логин сайта) и
bash /opt/football-runner/repo/server/install.sh
```

Внутри контейнера крутится `server/watch_loop.sh` — тот самый сторож:
- ждёт файл `results/RUN_REQUEST` и начинает прогон;
- если прогон оборвался (перезапуск контейнера, сбой), продолжает его с этапа сбора;
- при `FB_SCAN_AT=03:30` раз в сутки сам смотрит канал и запускает прогон, если
  появились новые видео.

Машины RunPod при этом защищены своим сторожем (`pod_watchdog.sh`): если
управляющий узел молчит 2,5 часа, машина удаляет себя сама. Лимит выбран больше
времени одной игры, чтобы перезапуск контейнера не убивал работу.

## Что осталось за рамками

- **`match_guid`** автоматически не находится: у текущей учётной записи сайта нет
  доступа к спискам матчей (`v1/league/` возвращает пусто, `match/timetable`
  требует `group_guid` лиги пользователя). Пока его вписывают в `plan.json` руками,
  без него статистика считается, но загрузка придерживается.
- **Скорости и пробег** этот прогон не считает: нужна разметка поля, см.
  `docs/PROMPT_autocalib.md` и `scripts/pitch_marker/`.
